---

## Problem Statement (Executive Summary)

The current mutation testing setup artificially inflates reliability metrics:
- **MSI = 100%** sounds perfect, but only covers **3 service directories** (~50 files).
- **97% of codebase is unmutated** and unverified at the mutation level.
- **Global line coverage = 28.33%** indicates broad behavior regression risk.
- **No mutation gate in CI/CD** — testing is opt-in local only.
- **Parallel coverage merge crashes** at 2GB memory due to XML aggregation.

**Impact:** False confidence in system reliability; regressions slip past code review.

---

## Solution Overview

### Objectives
1. **Expand mutation scope** from 3 modules to include `app/Services` and `app/Actions`.
2. **Gate mutation in CI/CD** with a Tier 2 post-PR check (30–45 min).
3. **Fix parallel coverage merge** by switching to sequential mode in CI.
4. **Improve app/Services coverage** from 35% to ≥ 60% to support mutation testing.
5. **Document best practices** for local and CI mutation workflows.

### Deliverables
- ✅ **Phase 1:** Root cause diagnosis (this directory).
- ✅ **Phase 2:** Strategic plan with scope/timeline.
- ✅ **Phase 3:** Implementation checklist (per-week tasks).
- ✅ **Phase 4:** CI/CD integration patterns (job templates).
- ✅ **Best Practices Guide:** Infection local + CI workflows.

## Quick Start for Developers

### See Your Test's Mutation Impact (Locally)

```bash
# Run Tier 2 mutation check (extended scope, ~40 min)
bash scripts/ci/check-mutation-tier2.sh

# Or just the 3 core modules (faster, ~2 hrs)
./vendor/bin/infection
```

If a mutant escapes, you'll see:
```
Escaped mutant in app/Services/CacheService.php:145
  - Operator increment removed
  - Original: $counter++
  - Mutated: (removed)
```

**Action:** Add an assertion to verify the side effect:
```php
test('increments counter on hit', function () {
    $service = new CacheService($cache);
    $cache->put('hits', 0); // Setup
    $service->hit('key');   // Trigger increment
    
    expect($cache->get('hits'))->toBe(1); // Assert the mutation escapes
});
```

## Key Decisions

### 1. Why Split into Tier 1 + Tier 2?

**Tier 1 (3 modules):** Narrow, expensive (~2 hrs), perfect metrics.  
**Tier 2 (app + modules):** Broad, fast (~40 min), realistic thresholds.

- **Tier 1** = Weekly offline (high confidence, high cost).
- **Tier 2** = Post-PR gated (low friction, moderate cost).

### 2. Why Sequential Coverage in CI?

Parallel + coverage merge = **OOM at 2GB**.  
Sequential coverage = **Memory-safe, accurate, reproducible**.

Trade-off: Sequential is slower locally, but only for CI reporting (OK).

### 3. Why app/Services First?

- Service layer is business-logic hub.
- High risk if tests are shallow.
- Reasonable scope for Tier 2 expansion (~900 lines code).
- Ready for mutation testing once coverage ≥ 60%.

## FAQ

### Q: Why does Tier 2 take 40 min every PR? Isn't that slow?

**A:** Trade-off:
- Fast: Skip mutation, miss regressions.
- Slow: 40 min per PR, catch mutations early.

**Optimization:** Selective mutation (Infection v0.29+) can run only **changed files** (future improvement).

### Q: What if a mutant escapes that I don't know how to test?

**A:** You're not alone. Document it:
```php
/**
 * @infection:ignore-all
 * Complex XYZ logic is hard to mutate-test; covered by integration tests.
 * See: tests/Integration/XyzTest.php
 */
public function complexMethod() { ... }
```

### Q: Will this slow down development?

**A:** Initially yes (learning curve). Long-term:
- Developers write better assertions (habits form).
- Fewer regressions in review (faster reviews).
- Net time gain after 4 weeks.

### Q: Can I skip mutation on my PR?

**A:** No (post-rollout). But you can:
- Run locally first: `bash scripts/ci/check-mutation-tier2.sh` (pre-push).
- Fix escaped mutants before pushing (faster than post-PR fixes).

### Issues Encountered?

4. **Team resistance:** Emphasize: mutation catches real bugs (show examples).
